# Build System & Project Scaffolding

## Overview

NanoBucket uses **Conan v2** for dependency management and **CMake** as the build system. The two are connected via Conan's `CMakeDeps` and `CMakeToolchain` generators, which emit CMake config files and a toolchain file that CMake consumes through a preset.

---

## Directory Layout

```
nanobucket/
├── CMakeLists.txt          # Root: project declaration, find_package, add_subdirectory
├── CMakeUserPresets.json   # Generated by Conan — DO NOT edit manually
├── conanfile.txt           # Dependency list + layout declaration
├── build/                  # All build artifacts (git-ignored)
│   └── Release/
│       ├── generators/     # Conan-generated CMake config files + toolchain
│       └── src/
│           └── nanobucket      # Compiled binary
├── config/                 # Runtime configuration files
├── cmake/                  # Reserved for hand-written CMake modules
├── docs/                   # Project documentation
├── include/
│   └── nanobucket/             # Public headers (interfaces + types)
├── lib/                    # Git submodules (future storage/auth plugins)
├── scripts/                # Developer workflow scripts
├── src/                    # All C++ source files
└── test/
    ├── unit/
    └── integration/
```

## How the Build Chain Works

```
conanfile.txt
     │
     ▼
conan install .  ──► build/Release/generators/
                          conan_toolchain.cmake   (sets compiler flags, paths)
                          CMakePresets.json        (defines "conan-release" preset)
                          Drogon/spdlog/...Config.cmake
                     CMakeUserPresets.json  ◄── placed in project root
                          (includes the above preset)
     │
     ▼
cmake --preset conan-release
     │  reads CMakeUserPresets.json → loads conan_toolchain.cmake
     │  runs find_package() → finds Conan-generated Config files
     ▼
cmake --build build/Release
     │
     ▼
build/Release/src/nanobucket
```

### Why `cmake_layout`?

`[layout] cmake_layout` in `conanfile.txt` tells Conan to mirror a standard CMake out-of-source build layout. It places all generated files under `build/<BuildType>/generators/` and sets `CMakeUserPresets.json` `binaryDir` to the absolute build path. This prevents the double-nesting (`build/build/`) that occurs when `--output-folder` is combined with an already-rooted layout.

## CMakeLists.txt Structure

### Root (`CMakeLists.txt`)

```cmake
cmake_minimum_required(VERSION 3.15)   # matches Conan preset minimum
project(nanobucket VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)             # Drogon requires ≥14; we use 17
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)          # no GNU extensions — improves portability
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)  # for clangd / IDE support

find_package(Drogon  REQUIRED)
find_package(spdlog  REQUIRED)
find_package(OpenSSL REQUIRED)
find_package(pugixml REQUIRED)
find_package(SQLite3 REQUIRED)         # target is SQLite::SQLite3

add_subdirectory(src)
```

### Sources (`src/CMakeLists.txt`)

Sources are added explicitly (no `GLOB_RECURSE`) so CMake detects new files only when the list is updated — this avoids stale incremental builds.

```cmake
add_executable(nanobucket
    main.cpp
    xml/S3XmlBuilder.cpp
    auth/SigV4Verifier.cpp
    auth/AwsSigV4Filter.cpp
    meta/SqliteMetaStore.cpp
    storage/LocalFsStorageEngine.cpp
    api/BucketController.cpp
    api/ObjectController.cpp
    api/MultipartController.cpp
)

target_include_directories(nanobucket PRIVATE ${PROJECT_SOURCE_DIR}/include)

target_link_libraries(nanobucket PRIVATE
    Drogon::Drogon  spdlog::spdlog
    OpenSSL::SSL    OpenSSL::Crypto
    pugixml::pugixml
    SQLite::SQLite3
)
```

## Developer Scripts

All scripts work from any directory (project root or `scripts/`). They resolve paths relative to `SCRIPT_DIR`.

### `scripts/setup.sh` — Install Conan dependencies

```bash
./scripts/setup.sh [options]

Options:
  -b, --build-dir DIR       Build directory (default: ./build)
  -t, --type TYPE           Build type: Release | Debug (default: Release)
  -p, --profile PROFILE     Conan profile
      --conan-args STR      Extra conan install arguments
      --no-conan            Skip conan install (use cached generators)
  -n, --dry-run             Print commands without running them
```

Must be run once after cloning or after changing `conanfile.txt`.

### `scripts/build.sh` — Configure + compile

```bash
./scripts/build.sh [options]

Options:
  -b, --build-dir DIR       Build directory (default: ./build)
  -t, --type TYPE           CMake build type (default: Release)
      --preset NAME         CMake preset (default: conan-release)
      --no-conan            Skip conan install step
  -n, --dry-run
```

Runs `cmake --preset <name>` then `cmake --build`.

### `scripts/start.sh` — Run the compiled binary

```bash
./scripts/start.sh [options] [-- <binary args>]

Options:
  -b, --build-dir DIR       Build directory (default: ./build)
  -t, --type TYPE           Build type to run (default: Release)
  -p, --port PORT           Listen port (default: 9000, or NANOBUCKET_PORT env var)
  -n, --dry-run

# Examples
./scripts/start.sh                     # Release on :9000
./scripts/start.sh -t Debug -p 9001   # Debug on :9001
NANOBUCKET_PORT=7480 ./scripts/start.sh   # via env var
```

Always `cd`s to the project root before exec so relative paths (`./logs/`, `./data/`) resolve correctly.

### `scripts/clean.sh` — Remove build artifacts

```bash
./scripts/clean.sh [options]

Options:
      --no-build            Don't remove build directory
      --source              Remove in-source CMake artifacts
      --conan-build-files   Remove Conan-generated helper scripts
      --conan-cache         Purge ~/.conan2 (destructive)
  -y, --yes                 Skip confirmation prompts
  -n, --dry-run
```

## Runtime Behaviour

### Port

Resolved in order: `-p` flag on `start.sh` → `NANOBUCKET_PORT` env var → default `9000`.

### Logging

Drogon's trantor logger writes to **stderr** at `kDebug` level. All incoming requests, 404s, and errors are visible in the terminal. File logging is deferred to the Configuration milestone when `config.json` is introduced.

### Shutdown

`SIGINT` (Ctrl+C) and `SIGTERM` both trigger `drogon::app().quit()`, which drains in-flight requests before the process exits.
