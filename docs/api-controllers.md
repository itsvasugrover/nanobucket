# S3 API Controllers

## Overview

Two Drogon `HttpController` classes handle all S3 HTTP operations. They translate between the S3 REST protocol and the internal `IStorageEngine` / `IMetaStore` interfaces. All XML is generated by `S3XmlBuilder`. Every route has the `AwsSigV4Filter` applied — unauthenticated requests receive `403 AccessDenied` before reaching any handler.

---

## File Map

```
src/api/
├── BucketController.h / .cpp   — bucket-level ops, ListObjectsV2, DeleteObjects, ACL stubs
├── ObjectController.h / .cpp   — object ops + full multipart upload lifecycle
└── ApiHelpers.h                — shared utilities (addStdHeaders, xmlErr, parseBucketKey, …)
```

Multipart upload operations (`CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`, `AbortMultipartUpload`, `ListParts`) all live in `ObjectController` because they share the `/{bucket}/{key}` URL space and are disambiguated by query parameters.

---

## Routing

S3 uses **path-style** addressing exclusively. Query parameters disambiguate operations that share the same URL pattern.

```
GET  /                                          → ListBuckets
PUT  /{bucket}                                  → CreateBucket
DELETE /{bucket}                                → DeleteBucket
HEAD /{bucket}                                  → HeadBucket
GET  /{bucket}?list-type=2                      → ListObjectsV2
GET  /{bucket}?uploads                          → ListMultipartUploads
POST /{bucket}?delete                           → DeleteObjects (bulk)
GET  /{bucket}?acl                              → GetBucketAcl  (stub)
PUT  /{bucket}?acl                              → PutBucketAcl  (stub, 200 OK)
GET  /{bucket}?cors|policy|lifecycle|…          → 404 stub

PUT  /{bucket}/{key}                            → PutObject  (or CopyObject if x-amz-copy-source present)
PUT  /{bucket}/{key}?partNumber=N&uploadId=X    → UploadPart
PUT  /{bucket}/{key}?acl                        → PutObjectAcl (stub, 200 OK)
GET  /{bucket}/{key}                            → GetObject
GET  /{bucket}/{key}?uploadId=X                 → ListParts
GET  /{bucket}/{key}?acl                        → GetObjectAcl (stub)
HEAD /{bucket}/{key}                            → HeadObject
DELETE /{bucket}/{key}                          → DeleteObject
DELETE /{bucket}/{key}?uploadId=X               → AbortMultipartUpload
POST /{bucket}/{key}?uploads                    → CreateMultipartUpload
POST /{bucket}/{key}?uploadId=X                 → CompleteMultipartUpload
```

### Drogon Route Registration

```cpp
// BucketController
METHOD_LIST_BEGIN
ADD_METHOD_TO(BucketController::listBuckets,  "/",     Get,
              "nanobucket::AwsSigV4Filter");
ADD_METHOD_TO(BucketController::handleBucket, "/{1}",  Get, Put, Delete, Head, Post,
              "nanobucket::AwsSigV4Filter");
ADD_METHOD_TO(BucketController::handleBucket, "/{1}/", Get, Put, Delete, Head, Post,
              "nanobucket::AwsSigV4Filter");
METHOD_LIST_END

// ObjectController — "/{1}/(.+)" regex matches keys that contain slashes
METHOD_LIST_BEGIN
ADD_METHOD_TO(ObjectController::handleGet,    "/{1}/(.+)", Get,    "nanobucket::AwsSigV4Filter");
ADD_METHOD_TO(ObjectController::handlePut,    "/{1}/(.+)", Put,    "nanobucket::AwsSigV4Filter");
ADD_METHOD_TO(ObjectController::handlePost,   "/{1}/(.+)", Post,   "nanobucket::AwsSigV4Filter");
ADD_METHOD_TO(ObjectController::handleDelete, "/{1}/(.+)", Delete, "nanobucket::AwsSigV4Filter");
ADD_METHOD_TO(ObjectController::handleHead,   "/{1}/(.+)", Head,   "nanobucket::AwsSigV4Filter");
METHOD_LIST_END
```

The trailing-slash variants of bucket routes (`/{1}/`) are required because s3cmd appends a `/` to bucket-level paths.

Each handler extracts bucket and key from `req->getPath()` directly via `parseBucketKey()` (in `ApiHelpers.h`) rather than relying on Drogon capture groups, which avoids quirks with percent-encoded slashes in keys.

## Shared Helpers — `ApiHelpers.h`

| Helper | Purpose |
|--------|---------|
| `addStdHeaders(res)` | Injects `x-amz-request-id`, `x-amz-id-2`, `Server: nanobucket` |
| `xmlErr(status, code, msg, key, bucket)` | Builds a standard S3 XML error response |
| `parseBucketKey(path)` | Splits `/bucket/key/with/slashes` into `{bucket, key}` |
| `rfc7231Date(tp)` | Formats a `time_point` as `Mon, 15 Jan 2024 10:30:00 GMT` |
| `isValidBucketName(name)` | 3–63 chars, lowercase alphanumeric + hyphens, no consecutive hyphens |

## Bucket Controller

### `GET /` — ListBuckets

```
Response: 200 + ListBuckets XML
```

1. `meta_->listBuckets()` → vector of `BucketInfo`
2. `S3XmlBuilder::listBuckets(buckets)` → XML body

### `PUT /{bucket}` — CreateBucket

```
Response: 200 (empty body)
Errors:   409 BucketAlreadyOwnedByYou, 400 InvalidBucketName
```

1. `isValidBucketName(bucket)` — reject if malformed
2. `storage_->createBucketDir(bucket)` — create directory; fail → 409 if already owned
3. `meta_->createBucket(bucket, ...)` — insert record; on failure roll back by calling `storage_->deleteBucketDir(bucket)`
4. Return 200

### `DELETE /{bucket}` — DeleteBucket

```
Response: 204 (empty body)
Errors:   404 NoSuchBucket, 409 BucketNotEmpty
```

1. `meta_->getBucket(bucket)` — 404 if missing
2. `meta_->deleteBucket(bucket)` — checks for existing object records, returns `BucketNotEmpty` if non-empty
3. `storage_->deleteBucketDir(bucket)` — remove directory
4. Return 204

### `HEAD /{bucket}` — HeadBucket

```
Response: 200 (empty body)
Errors:   404 NoSuchBucket
```

1. `meta_->getBucket(bucket)` — 404 if missing
2. Return 200

### `GET /{bucket}?list-type=2` — ListObjectsV2

```
Response: 200 + ListObjectsV2 XML
Errors:   404 NoSuchBucket
```

Query parameters:

| Parameter | Default | Notes |
|-----------|---------|-------|
| `prefix` | `""` | Filter key prefix |
| `delimiter` | `""` | Typically `/` for pseudo-directory listings |
| `max-keys` | `1000` | Page size, clamped to [1, 1000] |
| `continuation-token` | `""` | Opaque pagination cursor (`base64(first_excluded_key)`) |

1. Validate bucket exists
2. `meta_->listObjects(bucket, prefix, delimiter, maxKeys, token)` → `ListObjectsResult`
3. `S3XmlBuilder::listObjectsV2(result)` → XML body

### `GET /{bucket}?uploads` — ListMultipartUploads

```
Response: 200 + ListMultipartUploadsResult XML
Errors:   404 NoSuchBucket
```

1. Validate bucket exists
2. `meta_->listMultipartUploads(bucket)` → vector of `MultipartUploadInfo`
3. `S3XmlBuilder::listMultipartUploads(...)` → XML body

### `POST /{bucket}?delete` — DeleteObjects

```
Response: 200 + DeleteResult XML
```

Used by `s3cmd rb --recursive` and any SDK bulk-delete call.

Request body XML:
```xml
<Delete>
  <Object><Key>key1.txt</Key></Object>
  <Object><Key>folder/key2.txt</Key></Object>
</Delete>
```

1. Parse `<Delete><Object><Key>` elements using pugixml
2. For each key: `storage_->remove(bucket, key)` + `meta_->deleteObject(bucket, key)`
3. Collect keys into `deleted` list (errors into `errors` list)
4. `S3XmlBuilder::deleteObjects(deleted, errors)` → `<DeleteResult>` XML

### ACL / Sub-resource Stubs

| Request | Response |
|---------|---------|
| `GET /{bucket}?acl` | 200 + FULL_CONTROL ACL XML (owner = `"owner"`) |
| `PUT /{bucket}?acl` | 200 (silently accepted, ACL not stored) |
| `GET /{bucket}?cors` | 404 `NoSuchCORSConfiguration` |
| `GET /{bucket}?policy` | 404 `NoSuchBucketPolicy` |
| `GET /{bucket}?lifecycle` | 404 `NoSuchLifecycleConfiguration` |
| `GET /{bucket}?logging` | 404 `NoSuchLoggingConfiguration` |
| `GET /{bucket}?notification` | 404 `NoSuchNotificationConfiguration` |
| `GET /{bucket}?versioning` | 404 `VersioningNotEnabled` |
| `GET /{bucket}?website` | 404 `NoSuchWebsiteConfiguration` |
| `GET /{bucket}?tagging` | 404 `NoSuchTagSet` |

These stubs prevent `s3cmd info` and SDK calls from hitting the wrong handler or receiving unexpected response bodies.

## Object Controller

All object operations are dispatched through five handler methods (`handleGet`, `handlePut`, `handlePost`, `handleDelete`, `handleHead`). Each inspects query parameters and request headers to route to the appropriate `do*` implementation.

### `PUT /{bucket}/{key}` — PutObject

```
Response: 200 + ETag header
Errors:   404 NoSuchBucket
```

1. `storage_->put(bucket, key, body, &etag)` — atomic write via `.tmp` + `rename(2)`; MD5 ETag computed
2. Build `ObjectRecord{bucket, key, size, etag, contentType, now()}`
3. `meta_->putObject(record)`
4. Return 200 with `ETag: "<etag>"` header

### `PUT /{bucket}/{key}` + `x-amz-copy-source` — CopyObject

```
Response: 200 + CopyObjectResult XML
Errors:   404 NoSuchKey (source), 404 NoSuchBucket (destination)
```

The `x-amz-copy-source` header contains `/<sourceBucket>/<sourceKey>` (percent-encoded).

1. Parse and percent-decode `x-amz-copy-source`
2. `meta_->getObject(srcBucket, srcKey)` — 404 if missing
3. `storage_->copy(srcBucket, srcKey, dstBucket, dstKey)` — `std::filesystem::copy_file`
4. Use source ETag for the destination record (preserves multipart ETags)
5. `meta_->putObject(dstRecord)`
6. Return `CopyObjectResult` XML with ETag and `LastModified`

### `PUT /{bucket}/{key}?partNumber=N&uploadId=X` — UploadPart

```
Response: 200 + ETag header
Errors:   404 NoSuchUpload, 400 InvalidArgument
```

1. Validate `partNumber` ∈ [1, 10000]
2. `meta_->getMultipartUpload(uploadId)` — verify upload exists and matches bucket/key
3. `storage_->putPart(uploadId, partNumber, body, &etag)` — stored in `.multipart/<uploadId>/<partNumber>`
4. `meta_->putPart(uploadId, PartInfo{partNumber, etag, size, now()})`
5. Return 200 with `ETag: "<etag>"`

### `GET /{bucket}/{key}` — GetObject

```
Response: 200 + object bytes (zero-copy sendfile)
Errors:   404 NoSuchKey
```

1. `meta_->getObject(bucket, key)` — get record for headers
2. `storage_->objectPath(bucket, key)` — get filesystem path
3. `HttpResponse::newFileResponse(path)` — Drogon uses `sendfile(2)` under the hood
4. Set `Content-Type`, `ETag`, `Content-Length`, `Last-Modified` from record

### `HEAD /{bucket}/{key}` — HeadObject

```
Response: 200 with metadata headers, no body
Errors:   404 NoSuchKey
```

1. `meta_->getObject(bucket, key)` — 404 if missing
2. Return 200 with all metadata headers; body is always empty for HEAD

> **Drogon HEAD quirk**: Drogon converts `HEAD` to `GET` internally before calling filters and controllers. The auth filter uses `req->isHead()` to restore the original method when building the canonical request.

### `DELETE /{bucket}/{key}` — DeleteObject

```
Response: 204 (empty body)
```

Always returns 204, even if the key does not exist. This matches AWS behaviour — S3 `DeleteObject` is idempotent.

1. `storage_->remove(bucket, key)` — no-op if file absent
2. `meta_->deleteObject(bucket, key)` — no-op if record absent
3. Return 204

### `DELETE /{bucket}/{key}?uploadId=X` — AbortMultipartUpload

```
Response: 204 (empty body)
Errors:   404 NoSuchUpload
```

1. `meta_->getMultipartUpload(uploadId)` — 404 if missing
2. `storage_->removeParts(uploadId)` — delete all staged part files
3. `meta_->deleteMultipartUpload(uploadId)` — cascade-deletes part records
4. Return 204

### `POST /{bucket}/{key}?uploads` — CreateMultipartUpload

```
Response: 200 + InitiateMultipartUploadResult XML
Errors:   404 NoSuchBucket
```

1. Validate bucket exists
2. `meta_->createMultipartUpload(bucket, key, contentType)` — returns UUID `uploadId`
3. `storage_->initMultipart(uploadId)` — create `.multipart/<uploadId>/` directory
4. Return `InitiateMultipartUploadResult` XML

### `POST /{bucket}/{key}?uploadId=X` — CompleteMultipartUpload

```
Response: 200 + CompleteMultipartUploadResult XML
Errors:   404 NoSuchUpload, 400 InvalidPart
```

Request body XML:
```xml
<CompleteMultipartUpload>
  <Part><PartNumber>1</PartNumber><ETag>"etag1"</ETag></Part>
  <Part><PartNumber>2</PartNumber><ETag>"etag2"</ETag></Part>
</CompleteMultipartUpload>
```

1. Parse `[(partNumber, etag)]` from request XML
2. `meta_->listParts(uploadId)` — get stored part records
3. Validate: every client-supplied (partNumber, etag) must match a stored record
4. `storage_->assembleParts(bucket, key, uploadId, partNumbers)` — concatenate part files in order
5. Compute multipart ETag: `MD5(concat(raw_md5_bytes_of_each_part))` → `"<hex>-<partCount>"`
6. `meta_->putObject(record)` — store final object metadata
7. `meta_->deleteMultipartUpload(uploadId)` — clean up upload state
8. Return `CompleteMultipartUploadResult` XML with Location, Bucket, Key, ETag

### `GET /{bucket}/{key}?uploadId=X` — ListParts

```
Response: 200 + ListPartsResult XML
Errors:   404 NoSuchUpload
```

1. `meta_->getMultipartUpload(uploadId)` — validate and get upload info
2. `meta_->listParts(uploadId)` — get all part records
3. `S3XmlBuilder::listParts(...)` → XML body

### Object ACL Stubs

| Request | Response |
|---------|---------|
| `GET /{bucket}/{key}?acl` | 200 + FULL_CONTROL ACL XML — only if key exists (404 otherwise) |
| `PUT /{bucket}/{key}?acl` | 200 (silently accepted) |

`s3cmd cp` sends `GET ?acl` then `PUT ?acl` on the destination to copy permissions. Without these stubs, `PUT ?acl` would fall through to `doPutObject` and overwrite the object content with the ACL XML body.

## Standard Response Headers

Every response includes:

| Header | Value |
|--------|-------|
| `x-amz-request-id` | Random UUID per request |
| `x-amz-id-2` | Same as request ID (minimal server) |
| `Server` | `nanobucket` |

Object responses additionally include:

| Header | Source |
|--------|--------|
| `ETag` | Quoted MD5 hex digest from `ObjectRecord` |
| `Content-Type` | From `ObjectRecord.contentType` |
| `Content-Length` | From `ObjectRecord.size` |
| `Last-Modified` | RFC 7231 date from `ObjectRecord.lastModified` |

---

## Error Response Format

Every non-2xx response body is S3-compatible XML, even for 500 errors. SDKs parse the `<Code>` element to determine the exception type — a plain-text body produces an opaque `UnknownError`.

```cpp
cb(xmlErr(drogon::k404NotFound, "NoSuchKey",
          "The specified key does not exist.", key, bucket));
```

Produces:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<Error>
  <Code>NoSuchKey</Code>
  <Message>The specified key does not exist.</Message>
  <Key>photos/cat.jpg</Key>
  <BucketName>my-bucket</BucketName>
  <RequestId>…</RequestId>
</Error>
```
